# Zigbee2MQTT data in the backup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An optional switch puts Zigbee2MQTT's own backup (fetched over MQTT) inside every Nidoo backup; a Z2M that doesn't answer gives a saved-but-*partial* backup with a warning push and a `partial` flow port; a restore keeps the zip for download.

**Architecture:** A new `crates/nidoo/src/backup/z2m.rs` fetches the zip with Z2M's `bridge/request/backup` over its own short-lived MQTT connection (32 MiB packets), behind a `Z2mSource` trait so tests use a memory double. The job fetches it before writing the archive and passes it in `Sources`; the archive writes it as `z2m/<n>.zip` entries after `settings.json`; a skip reason travels out as `BackupDone::z2m_warning` to the record, the push and the flow step. Restore collects the entries into `Restored::z2m` and the restore job writes `data/zigbee2mqtt-restored.zip`, served by two new backup routes.

**Tech Stack:** Rust workspace; tokio; rumqttc 0.25; axum; serde; Leptos (web).

**Spec:** `docs/superpowers/specs/2026-11-12-backup-z2m-design.md` (extends `2026-11-11-backup-design.md`; the parent plan is `docs/superpowers/plans/2026-11-11-backup.md`).

**Plan decisions** (left to the builder by the spec):
- The request/response helper lives in `backup/z2m.rs` (used only by backups for now). It subscribes to `<base>/bridge/response/backup` *before* publishing the request, matches Z2M's echoed `transaction`, and ignores other responses.
- Bridge availability decides before any request: `Unknown` → not included (plain ok, no request); `Offline` → partial "Zigbee2MQTT is offline" at once; `Online` → fetch.
- The Z2M fetch runs after the FTP connect (an unreachable FTP still fails first); the existing `keep_alive` after the first bytes covers the extra wait.
- A new `BackupPart::Z2m` (`"z2m"`) shows during the fetch and the entries.

## Review Focus

1. **Old flows on a partial night**: a `backup.run` with only `ok` and `failed` wired takes `ok` when the outcome is partial, so the NAS still gets shut down. Test in Task 5.
2. **Z2M down never fails the backup**: offline, no answer, refused, oversized or garbled answers all upload a complete Nidoo file, with `ok: true` and a `warning` in the record. Tests in Tasks 2 and 4.
3. **Old files and records still read**: a format-1 file (no `z2m` in the manifest, no `z2m/` entries) restores; a `backup-last.json` without `warning` reads; a stored `backup` section without `include_z2m` reads as `true`. Tests in Tasks 1 and 3.
4. **A stale response from an earlier request** (another transaction id, or one sent before we subscribed) is not taken for ours. Test in Task 2.
5. **The network key stays private**: the `Restored` and `Sources` `Debug` output and every skip reason hold no zip bytes; the restored file is mode 0600. Tests in Tasks 3 and 6.
