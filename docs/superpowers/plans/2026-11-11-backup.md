# Backup and restore Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One encrypted backup file (settings, retained definitions, full history), sent to FTP or downloaded, run by a flow step or a button, and restored from the setup wizard on a fresh install.

**Architecture:** A new hub module `crates/nidoo/src/backup/` owns the file format (async tar → zstd → age, streamed through a bounded `tokio::io::duplex`), the database export/import (`COPY` in one `REPEATABLE READ` snapshot), the retained-topic list, the FTP store and the single-slot job on `Hub`. Wire types live in `nidoo-api/src/backup.rs`; the `backup.run` node kind lives in `nidoo-core`. Restore runs in a new restricted boot mode (`Mode::Restore`): setup router + database, no `Hub`, its own MQTT connection.

**Tech Stack:** Rust workspace; tokio; axum; sqlx 0.8 (`copy_out_raw` / `copy_in_raw`); `age` (passphrase, async), `async-compression` (zstd), `tar::Header` (already a dep) for entries; `suppaftp` (tokio, plain FTP); `libunftp` + `unftp-sbe-fs` as test-only FTP server; Leptos (web).

**Spec:** `docs/superpowers/specs/2026-11-11-backup-design.md` (committed as `7f14f071`).

**Plan decisions** (the spec leaves these to the builder):
- Tar entries are written by hand with `tar::Header::new_gnu()` onto an `AsyncWrite`, and read back by a small async reader. A table's `COPY` output is cut into entries of at most **8 MiB** (`db/<table>/<n>.copy`, `n` from `000001`), so each entry's size is known before its header and memory stays bounded. `tar x` still opens the file.
- `COPY … (FORMAT text)`. Tables = every table in schema `public` except `_sqlx_migrations` and `settings` (settings travel as `settings.json`, the exact stored rows `key → value`).
- `manifest.json` carries per-table row counts taken with `count(*)` inside the same snapshot. Restore compares each table's `COPY FROM` row count to it and fails on a mismatch (no silently truncated history).
- Retained documents are read by a fresh MQTT subscription (client id `<mqtt client_id>-backup`) to the backed-up families' filters, until **2 s** pass with no new message. The hub's in-memory stores are not used.
- The last-backup record is `data/backup-last.json` (atomic write, mode 0600). It survives a broken database.
- One system sensor, `system_last_backup` (timestamp of the last *successful* backup). There is no problem binary sensor: flows get the `failed` port.
- A push goes out only for a failed **FTP** backup (the unattended one), when "Notify me when a backup fails" is on. A browser download that fails or is interrupted only updates the record.
- The flow node's `timeout_minutes` is the job's time limit when the node starts the job. When it joins a running job, it is how long the node waits; on expiry the node takes `failed` ("time limit reached") and the job keeps running.
- The backup section is stored live (no restart), like `mobile`.
- Restore writes the `hub.json` fields at the end, in the same write that clears `restore`, rather than first. A failed restore therefore leaves `hub.json` unchanged.
- If the restore came from FTP and the backup's FTP settings differ from the source the user typed, the restored backup section takes the typed source (it just worked). Otherwise it is kept as is.
- No MCP tools in this version (the spec makes them optional).
- Upload restore and upload inspect send the password percent-encoded in the header `x-backup-password`, since the body is the raw file.

## Review Focus

1. **Serial counters after a restore**: `entity_state`, `entity_availability`, `climate_decision` and `assist_turn` have `bigserial seq`. After `COPY FROM`, each sequence must be moved past the restored maximum, or the next history row collides with or sorts before restored rows. Test in Task 3.
2. **A bad file is refused before anything is written**: wrong password, a truncated file, a file from a newer format or migration level. Each fails at the manifest, or fails without leaving partial rows behind (the job truncates on error). Tests in Tasks 4 and 10.
3. **FTP leftovers**: a `.partial` file is never listed, never counted toward `keep`, and pruned only after 24 h. Retention never deletes a file that does not match the backup name pattern. Test in Task 5.
4. **A flow run cancelled while it waits** (flow disabled, restart mode) does not cancel the backup: the job finishes and writes its record. Test in Task 8.
5. **Download closed mid-way**: the browser leaves during `GET /backup/download`. The job ends `Cancelled`, the slot frees at once (a new backup can start), and no push goes out. Test in Task 7.
