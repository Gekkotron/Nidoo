The table lists every topic the hub reads or writes, with its default prefix. "In" means the hub subscribes; "out" means the hub publishes. A prefix is shown in `<angle brackets>` or as its default, and the last column names the setting that moves it (see the [Settings reference](configuration.md)). Settings in the last column are written `[section] field`: `[topics]`, `[watchdog.gateway]` and `[watchdog.acl]` are in the **advanced** settings, `[groups]` and `[alarm]` too (see the [Settings reference](configuration.md#advanced)); `[weather]` is **Settings → Weather**, `[solcast]` **Settings → Solar forecast**, `[frigate]` **Settings → Cameras**, `[push]` **Settings → Notifications**, `[climate]` the Climate card of the setup wizard; `[mqtt] send_ha_birth` and `ha_status_topic` are in the `mqtt` object of `data/hub.json`. The broker user (the MQTT user of **Settings → Broker**) needs read and/or write on each topic accordingly.

## Notes

- **Reserved sub-trees.** Under a discovery prefix, the segments `ui`, `automation`, `virtual`, `push`, `weather`, `solar`, `network` and `flow_labels` are reserved: never publish discovery there. A topic in them is never read as discovery and never shows under `GET /api/v1/ignored`.
- **Climate documents never end in `/config`.** They cannot be read as discovery. The hub subscribes to `<prefix>/house`, `<prefix>/zone/+/+` and `<prefix>/zone/+/hold/set`, never `<prefix>/#`. `nidoo/push/responses` is always subscribed: a reply whose id starts with `alarm-` goes to the alarm, and the others (a tapped proposal button, for example) go to the climate engine when it is on.
- **Overlapping subscriptions.** The hub subscribes to `<discovery prefix>/#`, `<z2m_base>/bridge/{state,info,devices}` (not `bridge/#`, so a big backup answer never reaches the main connection), `<ui_prefix>/#`, `<automation_prefix>/#` and the flow label catalog topic (left out when one of those wildcards covers it, as the default `nidoo/flow_labels` is under `nidoo/#`). A push filter that falls inside one of those wildcards (the default `nidoo/push/…` under `nidoo/#`) is left out, so the broker does not deliver a notification twice.
- **Backed up.** The last column says whether a backup carries the topic: `yes` for definitions and user data, `no` for runtime state and for discovery the hub republishes itself, `—` for topics that are not retained or that another service retains. Rows that bundle several topics of one kind (weather, solar values, group and network entities, the alarm's runtime) have one value for all of them. The list lives in `crates/nidoo/src/backup/retained.rs`, and a test keeps this column in step with it.
- **Alerts raised inside the hub** (the Frigate bridge, watchdogs, flows, MCP) go to the push service in process, without the broker.
- **Retained history.** `nidoo/push/history` is the history itself: the hub adopts it at its first sync.
- **After each (re)connect** the hub waits for its subscription to be acknowledged, then 2 s more for the retained tokens, before it sends; alerts arriving meanwhile wait in the queue.
- **Flows and dashboards read as written.** An invalid flow or dashboard document is kept and shown with its reason, never run.
- **Broker permissions.** Give the hub user read and write on `nidoo/#` (or the narrower sets above), write on `nidoo-sound/speak`, `nidoo-sound/hold` (satellite speech and listening) and `nidoo-sound/+/remove/set` (removing a satellite), read on `<topic_prefix>/events` and `<gateway prefix>/+`, and for the ACL watchdog read on `$SYS/broker/log/#`. Mosquitto denies silently.
